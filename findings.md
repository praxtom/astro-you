AstroYou — Pre-Launch Review
Orientation
Stack: Vite 6 + React 19 + TypeScript SPA (Tailwind, Framer Motion, three.js) → Netlify CDN. Backend is ~55 Netlify Functions (modern export default + Config) with a shared lib layer. Firebase Firestore (client + Admin SDK) for data, Firebase Auth (Google + email OTP), Gemini for AI, astrology-api.io for charts, Razorpay for payments (credits + subscriptions), Resend for email. Build prerenders 430 SEO pages. Verification tooling: npm run test:functions (209 tests / 50 files), check:launch, check:market.

Main flows: (1) Auth — email-OTP or Google, guest→user migration, custom-token sign-in. (2) Onboarding — 5-step birth-data collection + geocoding. (3) Core astrology — unified /api/kundali (chartType switch) + horoscope/transit/compatibility, Firestore-cached. (4) AI — streaming /api/synthesis chat + per-minute /api/consult. (5) Payments — Razorpay top-ups → credit ledger, and tier subscriptions via webhook. (6) Retention — Atman (emotional/relationship memory), scheduled digests/nudges.

What's genuinely strong (verified, no action needed): the money-in path (server-derived prices, timing-safe HMAC, idempotent credit ledger, no double-grant, no amount tampering); OTP handling (HMAC-hashed at rest, attempt-limited, not brute-forceable); Firestore rules pin credits/subscription/referral fields entirely server-side; no committed secrets, no IDOR on user endpoints, admin gated by verified claim/email allowlist; thorough CSP + security headers. This is well above typical pre-launch hygiene.

No code was changed — this is review only.

🔴 Blockers
B1 — Every user's raw birth data (date/time/place) is readable by any logged-in user.
transit.ts:46 writes cache docs whose ID is ${dob}_${tob}_${pob}_${date} into the top-level transit_reports collection, and firestore.rules:121 is allow read: if request.auth != null. In Firestore, read includes list, and accounts are free (OTP-only) — so any signed-in user can enumerate the collection and harvest the exact DOB + time-of-birth + place-of-birth of everyone who ever opened Transit Oracle. That is the most sensitive data the product holds, cross-user exposed. This is a personal-data breach under India's DPDP Act.
Fix: the client never reads this collection directly (the function serves it via Admin SDK), so set allow read, write: if false; for transit_reports. Ideally also hash the doc ID (as weekly-astrology-context.ts already does) so birth data isn't in the key at all.

B2 — A committed type error makes the launch-gate and test suite un-runnable.
brain-nudges.ts:24 passes resolveUnsubscribeSecret() (returns string | undefined) into buildUnsubscribeUrl(secret: string). This fails tsc, so npm run test:functions (all 209 tests), npm run check:launch, and npm run check:market all abort at compile before running. You currently cannot execute your own pre-launch verification, and CI on tests is red. (Lint, app typecheck, and npm run build all pass — only the functions/gate toolchain is broken.)
Fix: const secret = resolveUnsubscribeSecret(); if (!secret) return undefined; return buildUnsubscribeUrl(uid, secret); — then run the gate and address whatever the 209 tests surface (they've been masked).

🟠 High
H1 — Transit reports are corrupted on cache hit and poisoned by upstream failures. cache.ts:39 does set({ ...(fresh), _cachedAt }); getTransitReport returns an array. Spreading an array yields {0:…,1:…,_cachedAt}, so every cache hit for the next 12h returns an object where .length is undefined → AI summary skipped and predictions breaks the any[] contract (TransitOracle renders empty / .map throws). Worse, astro-api.ts:952-954 returns [] on any non-200, which gets cached — one upstream blip breaks a chart's transits for 12 hours. Fix: wrap non-object payloads ({ value: fresh }) in cache.ts; make getTransitReport throw on !res.ok; never cache empty results.

H2 — Premium content is gated only in the client; the paywall is cosmetic. horoscope.ts:23-27 (and transit.ts, compatibility.ts, pdf-report.ts) call only verifyToken — no tier check — while the entitlement matrix marks weekly/monthly/yearly forecasts and transit alerts as paid-only. A free user with a valid token calls POST /api/horoscope {period:"yearly"} directly and gets the full premium forecast (and burns your paid astrology-API call). The correct pattern already exists in synthesis.ts:121 (isPaidSubscriptionActive). Fix: enforce canUseFeature/isPaidSubscriptionActive server-side on those endpoints.

H3 — Concurrent consult sessions dilute per-minute billing N×. startConsultSession (consult-session.ts:270) neither deducts credits nor checks for an existing active session; each session caps billing by its own maxBillableMinutes = floor(balance/price). Open K sessions in parallel, chat in all, and finalizes run sequentially — the first charges ≈balance→0, the rest charge min(cost,0)=0. User consumes K× the AI minutes, billed for one. Same root cause lets two browser tabs double-run a session. Fix: enforce a single active consult per user in the start transaction (resume the existing one), or escrow credits at start.

H4 — sign-horoscope.ts is unauthenticated with no rate limit, fronting the paid astrology API. It's the only public astrology endpoint missing the fail-closed per-IP limiter its siblings use, and date is only format-checked, so varying it defeats the cache. An anonymous attacker loops POST /api/sign-horoscope across date values → unbounded billable upstream calls + Firestore writes, no account needed. Fix: add allowAnonRequest(req, "sign_horoscope", …) and bound date to ±1 year.

H5 — No timeout on ~50 outbound astrology-API fetches vs Netlify's function limit. astro-api.ts has zero AbortSignal usage. A hung (not errored) upstream socket holds the function until the platform kills it → opaque 502 instead of the clean JSON error the code would produce. Most dangerous in pdf-report.ts, which moves credits sequentially around a slow PDF render — a timeout mid-flow risks charged-but-no-report. Fix: shared fetchWithTimeout(AbortSignal.timeout(8000)); for pdf-report, reserve-then-finalize credits (auto-refund on failure) or move to a background function.

H6 — Synthesis can charge a credit but return nothing, and can lose the assistant reply. After reserving 1 credit (synthesis.ts:127), buildUserContext runs outside the refund try/catch — a Firestore blip throws a 500 and the credit is never refunded. Separately, the assistant reply is persisted only client-side after the stream ends (Synthesis.tsx:726); closing the tab before that write loses the answer while the credit stays spent, and interactionId (conversation continuity) is dropped via a swallowed .catch(()=>{}). Fix: wrap context-build in the refund path (or build before charging); persist the assistant message + interactionId server-side.

H7 — No consent/notice layer, and the privacy policy misstates the law. AuthModal.tsx has zero Terms/Privacy acceptance; firebase.ts:21 fires GA4 unconditionally at load (pre-consent, for EU visitors too). The policy (legal-policies.ts) never names Gemini/astrology-api.io/Resend/GA/Razorpay as processors, states no retention periods, and says children are "under 13" — India's DPDP defines a child as under 18 with parental-consent duties. Emotional-state data is arguably GDPR special-category. Fix: add a consent line + policy links at signup/onboarding, gate GA4 behind consent, name the processors, add retention + international-transfer + grievance-officer sections, change 13→18.

H8 — No error monitoring, uptime check, or health endpoint. ErrorBoundary.tsx:24 is a placeholder comment; no Sentry/anything in the tree; admin-launch-readiness is admin-POST-only so a prober can't use it. Server errors go to Netlify logs nobody is alerted on; frontend errors go nowhere. At launch you'd learn about an astrology-API or Razorpay outage from users. Fix: add a public GET /api/health, wire Sentry (@sentry/react + shared reportError() in function catches), enable Netlify failure notifications.

H9 — Debug console.log leaks intimate PII in the production frontend. atman.ts (13 sites: emotional state, relationship names, life events), useKundali.ts (birth data every fetch), Compatibility.tsx:201 (full match data). Anyone with DevTools sees it; for a "we remember your emotional journey" product this is a trust problem. Fix: delete or gate on import.meta.env.DEV; add ESLint no-console for src/.

H10 — Scheduled digest/nudge jobs stall at scale. scheduled-users.ts:58 persists the pagination cursor only once, after the loop, and the default deadlineMs is 60s — longer than Netlify's scheduled-function platform cap. Callers pass no override. Under load (digest does sequential per-user work with up to 4 astrology calls each), the platform kills the run before the cursor write → next run reprocesses the same head users and the tail is delayed/skipped. Fine for a tiny initial userbase, degrades as you grow. (Duplicate sends are prevented by idempotency, so it fails as "no progress," not spam.) Fix: persist the cursor after each page inside the loop, and set deadlineMs well under the platform cap (e.g. 8s) or convert to -background functions.

H11 — A referee's email is exposed to the referrer and survives the referee's deletion. referrals.ts:75 stores refereeEmail in a doc under the referrer's tree, which firestore.rules:108 lets the referrer read directly via the client SDK. delete-account only deletes the referee's own tree, so their email persists in someone else's data forever — an erasure-request failure. Fix: don't store the raw email (mask it), set referrals read to if false and serve masked data via the API, and add a collection-group cleanup on referee deletion.

🟡 Medium
Corrupt localStorage JSON white-screens the whole app. Synthesis.tsx:240, Dashboard.tsx:91 parse GUEST_PROFILE/PROFILE unguarded; the only boundary is the root one, and the bad key is never cleared → permanent lockout on reload. useTransit.ts:40 does the same but leaves the hook loading:true forever. Guard + clear the key (the useUserProfile pattern is already correct).
Single global error boundary. App.tsx:72 is the only one — any one dashboard card that throws replaces the entire app with the error screen. Wrap routes/cards individually.
Paying subscriber locked out of chat at 0 credits. Synthesis.tsx:502 client-gates on credits<=0 even though the server exempts active paid subscribers — contradicts the "unlimited" promise. Also ConsultChat.tsx:391 ignores server error SSE events, so mid-consult Gemini failures show no error while the meter runs.
Onboarding never confirms the birth place resolved. Nominatim failures are swallowed (LocationInput.tsx:118); a user who types an unresolvable place finishes onboarding, then every chart call fails with a generic 500 and no hint. Block completion if the final-step preview fails.
verify-otp deletes the code before minting the token (verify-otp.ts:110) — if createCustomToken/createUser fails, retrying the valid code says "No code found," forcing a 60s wait. Mark used only after the token mints.
Scheduled functions have no in-code invocation guard (defense-in-depth; platform-restricted today), rate-limit fail-open gaps — the authenticated paid scopes (horoscope, transit, compatibility, astro_*) fail open on a limiter outage, and the real consult scope ai_consult isn't in the fail-closed list (rate-limit.ts:30); consult-start has no limit at all. Add them to FAIL_CLOSED_SCOPES.
FIREBASE_SERVICE_ACCOUNT missing → opaque module-load crash across all ~50 functions (firebase-admin.ts:11). Validate and throw a named error like razorpay-order.ts does.
Privacy hygiene: real names sent to astrology-api.io unnecessarily (astro-api.ts:163) despite the policy saying only calculation fields are shared; no TTL/retention on otps, analyticsEvents, chats, consult transcripts (only rateLimits has one); consult-message.ts:160 logs AI-error bodies that synthesis.ts deliberately refuses to (can echo chat content); send-otp.ts:144 logs the Resend error body (can contain the recipient email). Account deletion leaves analyticsEvents, trustModerationQueue, expertApplications, and referrer-side referral records behind — extend delete-account to purge/anonymize them.
Report tier caps not enforced (pdf-report is credit-gated only — decide if the advertised per-tier limits are real). .env.example missing 8 referenced vars (batch-size knobs, DIGEST_FROM_EMAIL, VITE_ENABLE_SERVER_ANALYTICS).
Accessibility on critical flows: Onboarding birth-date/time inputs have no htmlFor/id (Onboarding.tsx:758); Synthesis chat <textarea> and chart-type <select> have no accessible name. Screen readers announce unlabeled fields on your main conversion step.
Wildcard CORS Access-Control-Allow-Origin:* on compatibility.ts:99 (only endpoint that sets CORS; unnecessary for same-origin /api/*). Analytics device ID survives logout (AuthContext.tsx:191 doesn't clear astroyou:analytics_id), linking successive accounts on a shared browser. export-data omits the user's payment/audit/analytics records and returns raw err.message on 500.
🟢 Nice-to-have
884 kB three.js chunk (236 kB gz) loads on the Landing page 600ms in, unconditionally (Landing.tsx:125) — hurts LCP on the mid-range Indian Android devices you're targeting. Gate on viewport/saveData or use a CSS starfield on mobile.
/api/credits/use throws on every call — applyCreditChange with no ledgerId hits .doc(undefined) which throws. Currently dead code (no caller), but delete or fix it before it's wired up.
OTP boxes reject paste (AuthModal.tsx:143) — users retype the emailed code under a 5-min expiry. Blank screen during auth boot (no splash while AuthContext awaits Firestore + credits-init).
Google Fonts loaded from Google (index.html:64) leaks visitor IPs pre-consent — self-host. Self-referral farming possible across accounts (gate reward on referee's first paid action if abused).
analyticsEvents grows unbounded (one doc/event, no cleanup) — add a TTL. Scripts hard-require pnpm while docs use npm. Empty-interface lint warning at CelestialEngine.tsx:52.
Launch readiness verdict: Not ready — but close (roughly 2–4 days of focused fixes)
The engineering foundation is strong — payments, auth, OTP, and Firestore rules are better than most launches. But there is a live cross-user exposure of every user's birth date/time/place (B1) and the project's own launch-gate can't run (B2), and those two alone mean you should not go live today. The privacy/consent gaps (H7) also carry real DPDP/GDPR liability for an India-first launch collecting emotional data.

Top 3 to fix before launching:

Lock down transit_reports — set allow read, write: if false in firestore.rules (and stop putting birth data in cache doc IDs). This is a one-line stop-gap for an active data breach.
Fix the brain-nudges.ts:24 type error, then run npm run test:functions and check:launch and resolve whatever the now-unmasked 209 tests surface — you can't ship what you can't verify.
Enforce entitlements server-side on the premium endpoints (H2) and fix the transit cache corruption (H1) — right now core paid features are either free or broken.
